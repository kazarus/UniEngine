# UniEngine 下一阶段路线图

> 基线：`ai-dev-20261017` / `f200236`
> 日期：2026-10-18
> 定位：开源库本体已完成六库真机验证与兼容性修复，下一阶段以稳定化、方言矩阵和 API 收口为主，不继续扩大 API 面。

---

## 1. 当前基线

- PostgreSQL / MySQL / SQL Server / Oracle / TiDB / 达梦真机测试
- 根模块 272 个单测，覆盖率约 **90.2%**
- CI：`build` / `vet` / `gofmt` / `test -race` / 覆盖率门槛 85% / 3 个 fuzz smoke
- 注册表一表多类、共享锁、COW 快照
- Oracle 100 行/页、达梦 100 行/页批量上限
- 引擎级 `WithTx`（context 版已放弃）
- `GetTableByClass` / `ExistConstOn` / 达梦与 Oracle 统一分页参数

明确不做：

- context 版 `WithTx`
- `staticcheck` / `govulncheck` / `golangci-lint`
- 为兼容某一家国产库而改变 `Provider` 语义
- 历史命名风格（PascalCase / `this` / `eror`）全量重写

## 2. 下一阶段三条主线

### 主线 A：数据库矩阵与正确性

| 优先级 | 工作 | 说明 |
|---|---|---|
| P1 | 金仓 KingbaseES 真机 | `DtKINGES` 目前仅按 PG 族复用，需验证 `information_schema`/UPSERT/占位符 |
| P1 | openGauss 真机 | 与 PostgreSQL 存在差异，重点验证 `ON CONFLICT`、`COPY`、元数据 |
| P1 | PolarDB 真机 | `Supplier=DtPOLODB` + `InsertP` COPY 路由 |
| P1 | Taurus 真机 | MySQL 协议差异；需确认 `float/double`、序列等历史问题 |
| P2 | 达梦固定测试环境 | 当前真机覆盖依赖外部实例，CI 未固定 |
| P2 | Oracle 多 schema / 同义词 / 物化视图 | 当前 `USER_*` 边界已文档化；按真实需求决定是否扩展 |
| P2 | `ExistConstOn` 扩展到非 `CtDF` | 目前只解决默认值列名歧义 |

验收：

- 每个方言至少一组 CRUD + 批量 + 元数据真机用例
- 新方言只增加 `Provider`/`dbFamily` 映射，不要求应用改 SQL 分支
- 失败场景有明确错误，不静默写错数据

### 主线 B：工程质量与安全

| 优先级 | 工作 | 说明 |
|---|---|---|
| P1 | 加密/验签密钥轮换 | 当前只支持单密钥；需要 key id/版本与迁移窗口 |
| P1 | 性能基准固定化 | 批量页大小、`SelectL` 扫描、COPY/INSERT ALL 分方言基线 |
| P2 | API 清理 | `Instance`/`DataUser`/`ParentTab` 等废弃面(`DecryptResult` 已于 v2 删除;`HasField` 有下游消费者,保留) |
| P2 | prepared statement 缓存 | 每查询 `PrepareContext`；是否引入缓存需基准证明收益 |
| P2 | README 拆分 | 拆为使用/方言/迁移/安全四份，降低漂移 |

验收：

- 安全密钥可轮换，旧密文仍可读
- benchmark 有基线阈值，回归可发现
- 废弃 API 有迁移表；不破坏现有调用方

## 4. 评分视角

当前库本体约 **90/100**，主要失分不在功能，而在：

- 部分声称支持的方言缺真机证据
- 安全密钥生命周期不完整
- 历史 API/命名增加维护成本
- 文档体量过大，存在漂移

建议不要继续加新功能；先把方言矩阵和安全生命周期做完，再考虑 v1.0 API 冻结。

---

## 5. 明确不建议现在做

- context 版 `WithTx`：需要改造大量下游函数签名，收益低于成本
- 为单一国产库改 `Provider` 语义：会破坏下游按 `Provider` 分支的 SQL
- 全量风格重写：diff 大、风险高、不产生行为收益
- 引入重型静态分析工具：历史命名会产生噪声，先靠覆盖率、fuzz、`go vet` 控制
